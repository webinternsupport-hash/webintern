DATA ARCHITECTURE
================================================================================

IndexedDB Database: InternshipComLocalDB (Version 1)

Object Stores with Account Scoping:
1. users [userId]
   - Store: { userId, name, email, phone, college, department, degree }
   
2. profiles [id] → userId
   - Extended profile data scoped to user
   
3. enrollments [id] → userId, (userId+internshipId)
   - { userId, internshipId, internshipTitle, status, progress, ... }
   - Unique index prevents duplicate enrollments
   
4. applications [id] → userId, internshipId
   - Application records
   
5. offerLetters [id] → userId, enrollmentId
   - { userId, enrollmentId, internshipId, candidateName, issueDate, ... }
   
6. certificates [id] → userId, enrollmentId
   - { userId, enrollmentId, internshipId, certificateNumber, ... }
   
7. activities [id] → userId, enrollmentId
   - Activity and submission history
   
8. progress [id] → userId, enrollmentId
   - Progress tracking by enrollment
   
9. documents [id] → userId, type
   - Document storage (PDFs, blobs)
   
10. session [key]
    - Session metadata only (tokens stored in localStorage)

ACCOUNT SCOPING:
Every record includes userId field that ties it to specific user
All reads filter by userId to prevent cross-account data access

KEY DISTINCTION: SESSION vs PERSISTENT DATA
================================================================================

SESSION DATA (Cleared on Logout):
- access_token (JWT)
- user_profile (current user in localStorage)
- Session-specific information
- Lifetime: Current browser session

PERSISTENT DATA (Remains After Logout):
- Enrollments (IndexedDB)
- Certificates (IndexedDB)
- Offer letters (IndexedDB)
- Profile information (IndexedDB)
- Activity history (IndexedDB)
- Lifetime: Until user deletes account

WHY THIS MATTERS:
Users expect to logout and then login again without losing their data.
Before: Logout → Data deleted → Login → Data gone ❌
After: Logout → Session cleared → Login → Data restored ✅

================================================================================
BEFORE vs AFTER COMPARISON
================================================================================

BEFORE IMPLEMENTATION:
Problem: User creates account, enrolls, logs out, logs in → enrollment LOST
Root Cause: All data stored in localStorage/sessionStorage
Logout cleared everything
Result: User must re-enroll every time they log in

AFTER IMPLEMENTATION:
Solution: Persistent data in IndexedDB, session tokens in localStorage
Logout clears tokens only, data remains in IndexedDB
Login restores all previous data
Result: User sees all previous enrollments immediately upon login

IMPACTS:
✅ Better user experience
✅ Offline-first architecture
✅ No more data loss on logout
✅ Faster subsequent logins
✅ PWA/Android app fully supported
✅ Multiple accounts on same device

KNOWN LIMITATIONS (BY DESIGN)
================================================================================

Data Does NOT Sync:
❌ Another phone
❌ Another browser
❌ Another computer
❌ After clearing cache
❌ After uninstalling app

Why This Limitation:
✓ Requirement: NO external database
✓ This is the designed trade-off
✓ Privacy: Data stays on device
✓ Offline: Works without server
✓ Simplicity: No cloud sync needed

This Limitation is Acceptable Because:
✓ Clearly documented
✓ Expected behavior for local storage
✓ Users aware of device-specific persistence
✓ Best for privacy and offline capability
